## 0. Итог аудита и решения, которые нельзя отложить

### 0.1. Главный вывод

В исходной версии v4.0 слишком много места отведено исследованию точности прогноза токенов. В регламенте нет отдельного начисления баллов за MAPE, R² или качество конформного интервала. Побеждает решение, которое **набирает максимальную сумму reward за правильно решённые задачи при общем ограниченном бюджете**.

Следовательно, прогноз стоимости — инструмент принятия решения, а не самостоятельная цель. В оставшиеся два дня нельзя одновременно качественно проверить 19 теорий, разработать новый оценщик, обучить модель, переписать солверы и провести полноценную статистическую оценку. Такой план повышает риск не пройти сборку или отборочный прогон.

Целевой результат команды — не самый сложный оценщик, а минимальный устойчивый контур:

1. корректно прочитать все 100 задач и их `reward`;
2. определить, какие задачи имеет смысл брать;
3. оценить расход на уровне задачи и каждого LLM-вызова;
4. не запускать запрос, если его безопасный резерв не помещается в общий остаток;
5. использовать один из четырёх разрешённых моделей через openJiuwen;
6. проверить результат доступной проверкой и сохранить `answer.txt` в каталоге задачи;
7. после каждого завершения пересчитать остаток бюджета и порядок задач.

## 1. Цель и критерий победы

### 1.1. Целевая функция

Для каждой задачи `i` известен `reward_i`. Пусть `solved_i = 1`, только если задача завершена и её ответ принят скрытым тестированием; иначе `0`.

Нужно максимизировать:

`TotalScore = Σ(reward_i × solved_i)`

при ограничениях:

- суммарная стоимость всех LLM-вызовов не превышает общий бюджет `B`;
- время выполнения не превышает 1 час;
- используются только четыре разрешённые модели через прокси;
- результат каждой решённой задачи сохранён в правильном `answer.txt`.

Ошибочный ответ даёт 0 баллов. Нерешённая до исчерпания бюджета задача также даёт 0 баллов. При одинаковом score выигрывает решение, потратившее меньше токенов.

**Важно:** reward не является оценкой сложности. Нельзя выводить стоимость или решаемость задачи из её баллов. Reward используется как ценность результата при выборе порядка задач.

### 1.2. Приведение токенов к единице бюджета

Регламент задаёт стоимость в эквиваленте выходных токенов:

`cost = output_tokens + input_tokens / 10`

Внутренний учёт хранит дробное значение. Для резерва до вызова допускается округление вверх. Кеш провайдера не уменьшает стоимость.

Reasoning входит в выходной расход. Если `reasoning_tokens` уже включены в `completion_tokens`/`output_tokens`, повторно прибавлять их запрещено. Если прокси отдаёт reasoning отдельно и не включает его в общее количество output, нормализатор добавляет его один раз. Это поведение должно быть подтверждено тестом на реальном ответе прокси.

Формула должна применяться ко всем запросам: основной prompt, повторные попытки, исправления, self-check, пробные вызовы и автоматические retries SDK. Неучтённых LLM-вызовов быть не должно.

### 1.3. Главные метрики

В следующем порядке:

1. `TotalScore` — основной результат.
2. `solved_count` и доля решённых задач.
3. `budget_used` и остаток бюджета.
4. Количество запросов, не отправленных из-за недостаточного резерва; количество остановок по времени.
5. Фактическая стоимость на задачу и на успешную задачу.
6. Качество оценщика: MAE, MdAPE, WAPE, MAPE на положительных расходах, доля недооценки верхней границей.
7. Время выполнения и задержка принятия решения.

`R²`, bootstrap и проверки статистической значимости допустимы как аналитика, но не являются гейтами сдачи. На 8–20 задачах не публиковать их как доказательство устойчивого превосходства.

## 3. Архитектура решения

### 3.1. Поток выполнения

```text
run_agent.py
  ├── RuntimeConfig / BudgetProvider
  ├── TaskLoader
  │     ├── читает все каталоги задач
  │     ├── получает task_id, reward и фактический task.json
  │     └── проверяет доступность answer.txt
  ├── FeatureExtractor
  ├── SolverRegistry
  │     ├── deterministic solver
  │     ├── coding solver
  │     └── generic solver
  ├── CostEstimator
  ├── SolveabilityChecker
  ├── TaskPlanner
  │     └── строит набор задач с максимальным ожидаемым reward
  ├── BudgetLedger
  │     ├── reserve() до LLM-вызова
  │     ├── settle() после ответа/ошибки
  │     └── не допускает гонку между workers
  ├── OpenJiuwenGateway
  │     └── openJiuwen Core → разрешённая модель → LLM proxy
  ├── SolverExecutor
  │     ├── выполняет шаги задачи
  │     ├── передаёт usage в BudgetLedger
  │     └── проверяет результат
  ├── AnswerStore
  │     └── атомарно сохраняет answer.txt
  └── RunReporter
        ├── краткий итог в stderr
        └── технические trace в /tmp
```

### 3.2. Принципы архитектуры

- **Общий бюджет — единый источник истины.** Ни оценщик, ни отдельный worker не ведут независимый счётчик.
- **Каждый LLM-вызов проходит через один шлюз.** Солверы не создают собственные клиенты и не обходят `BudgetLedger`.
- **Сначала точный дешёвый способ.** Если задача полностью покрывается детерминированным решателем, LLM не вызывается.
- **Неизвестный тип не должен ронять весь процесс.** Он передаётся универсальному решателю с исходной инструкцией и реальной структурой задачи.
- **Проверка не должна изменять задачу.** Solver не подменяет тесты, проверяющие файлы и исходные условия.
- **Сохранение происходит сразу после подтверждённого решения.** Не ждать завершения всех 100 задач.
- **Перепланирование выполняется после каждого завершённого задания.** Фактическая стоимость обновляет оценки для следующих задач.
- **Параллелизм вводится только после доказанного корректного резервирования.** Начальное значение — 1 worker.

### 3.3. Реестр компонентов

Реестр сохраняется, но его не нужно усложнять плагинной системой. Достаточно явных фабрик:

- `build_estimator(config) -> CostEstimator`
- `build_policy(config) -> TaskPlanner`
- `build_solver(task) -> Solver`
- `build_llm_gateway(config) -> OpenJiuwenGateway`

Неизвестное имя компонента должно приводить к понятной ошибке конфигурации на старте. Ошибка оценщика во время выполнения может переключить его на fallback; ошибка шлюза модели не должна молча переключать запрос на неразрешённый endpoint или локальную модель.

## 4. Контракты данных и API между модулями

Названия полей ниже — внутренний Python-контракт. Они не означают, что организаторы обязаны использовать те же имена в `task.json`.

```python
from dataclasses import dataclass
from typing import Literal

@dataclass(frozen=True)
class Task:
    task_id: str
    path: str
    reward: float
    task_type: str | None
    raw: dict                 # исходный task.json без потери полей
    instruction: str | None   # извлекается адаптером из фактической схемы

@dataclass(frozen=True)
class CostEstimate:
    expected_cost: float      # input/10 + output
    upper_cost: float         # эмпирический риск-ориентированный прогноз
    expected_input_tokens: float
    expected_output_tokens: float
    confidence: Literal["low", "medium", "high"]
    model: str
    solver: str
    drivers: tuple[str, ...]

@dataclass(frozen=True)
class TokenUsage:
    input_tokens: int
    output_tokens: int        # включает reasoning, если так считает proxy
    reasoning_tokens: int     # диагностическое поле, не всегда добавляется
    total_cost: float         # output + input / 10
    source_fields: tuple[str, ...]

@dataclass(frozen=True)
class Decision:
    action: Literal["accept", "reject_cost", "reject_impossible", "reject_time"]
    reason: str
    planned_cost: float
    expected_reward: float

@dataclass(frozen=True)
class SolveResult:
    task_id: str
    status: Literal["solved", "failed", "impossible", "budget_exhausted", "timeout"]
    answer: str | None
    actual_cost: float
    model: str | None
    attempts: int
    reason: str
```

### 4.1. Бюджетный реестр

`BudgetLedger` — обязательный компонент, а не вспомогательная аналитика.

Методы:

```python
class BudgetLedger(Protocol):
    def reserve(self, request_id: str, estimated_input: int,
                max_output: int, safety_margin: float = 0.0) -> Reservation | None: ...
    def settle(self, request_id: str, usage: TokenUsage) -> None: ...
    def release_failed(self, request_id: str, *, definitely_not_sent: bool) -> None: ...
    def remaining(self) -> float: ...
```

Правила:

1. Перед отправкой запроса резервируется стоимость не меньше `estimated_input/10 + max_total_output + margin`. `max_total_output` должен учитывать и обычные completion-токены, и reasoning, если proxy включает reasoning в выходной расход. Нельзя считать, что параметр `max_output_tokens` ограничивает reasoning, пока это не подтверждено тестом конкретной модели/proxy.
2. Резерв проверяется и списывается атомарно под `threading.Lock`/эквивалентной синхронизацией.
3. Если резерва недостаточно, запрос не отправляется; задача получает `reject_cost` или текущий solver делает безопасную остановку.
4. После ответа резерв сверяется с фактическим usage. Неиспользованный остаток возвращается в доступный бюджет.
5. Если запрос мог быть принят прокси, но ответ потерян, нельзя автоматически считать его бесплатным. Резерв сохраняется или списывается по консервативной оценке.
6. Автоматические retries должны быть отключены или прозрачно учтены. Один вызов `Runner` не должен скрывать несколько оплачиваемых запросов.
7. При параллельной работе workers нельзя резервировать одну и ту же сумму повторно.
8. Счётчик не должен становиться отрицательным. Перед отправкой проверяется инвариант `spent + reserved <= B`.
9. Источник окончательного учёта — прокси организаторов. Локальный Ledger предотвращает очевидный перерасход, но не заменяет проверку фактического поведения прокси.

### 4.2. Нормализация usage

`UsageNormalizer` поддерживает фактически полученные поля, например:

- вход: `prompt_tokens` или `input_tokens`;
- выход: `completion_tokens` или `output_tokens`;
- детализация: `completion_tokens_details.reasoning_tokens` или аналогичное поле.

Нужно проверить реальные названия полей в ответе организаторского прокси. Нельзя считать, что любой OpenAI-compatible сервер использует одинаковую семантику usage.

Обязательные тест-кейсы:

- usage с `prompt_tokens` и `completion_tokens`;
- usage с `input_tokens` и `output_tokens`;
- reasoning включён в output — не прибавляется второй раз;
- reasoning отдельный и не включён в output — прибавляется один раз;
- отсутствующий usage;
- нулевой usage для детерминированного solver;
- usage после повторного вызова;
- usage при исключении/обрыве соединения.

## 5. Интеграция openJiuwen и LLM proxy

### 5.1. Что именно используем

Использовать Python SDK **openJiuwen Core**, пакет `openjiuwen`. Не устанавливать `workswarm`/`jiuwenswarm` в runtime без прямого указания организаторов: это отдельное прикладное приложение, а не минимальная библиотека, нужная для запуска harness.

Зафиксировать `openjiuwen==0.1.20.post1`, если этот релиз проходит сборку и smoke-тест. В PyPI для него указан Python `>=3.11,<3.14`; официальный README Core показывает создание `WorkflowAgent`, настройку `ModelClientConfig` и `ModelRequestConfig`, регистрацию workflow и запуск через `Runner.run_agent`. Перед финальной сборкой все транзитивные зависимости также закрепить lock-файлом.

### 5.2. Требуемый путь вызова

Все запросы к языковой модели в production-пути должны проходить через `OpenJiuwenGateway`, реализованный на официальных интерфейсах openJiuwen Core. Внутренний интерфейс шлюза:

```python
class OpenJiuwenGateway(Protocol):
    async def generate(
        self,
        *,
        model: str,
        messages: list[dict],
        max_output_tokens: int,
        request_id: str,
    ) -> LLMResult: ...
```

Шлюз отвечает за:

- создание/переиспользование конфигурации SDK;
- выбор только разрешённой модели;
- передачу адреса и ключа proxy в `ModelClientConfig`;
- вызов через `LLMComponent`/`WorkflowAgent` и `Runner` либо другой документированный интерфейс Core, проверенный на закреплённой версии;
- получение raw usage и передачу его нормализатору;
- передачу резерва в `BudgetLedger` до отправки;
- исключение непредусмотренных сетевых направлений.

Не следует создавать новый workflow и новый runner без необходимости на каждый токеновый шаг, если это приводит к лишним накладным расходам. Инициализацию и повторное использование компонентов следует проверить простым нагрузочным тестом.

### 5.3. Переменные окружения

Регламент передаёт:

- `LLM_BASE_URL` — адрес proxy;

SDK quick start использует параметры `api_base`, `api_key`, `client_provider`, `model` (а в примере — переменные `API_BASE`, `API_KEY`, `MODEL_PROVIDER`, `MODEL_NAME`). ## 6. Оценка стоимости задачи

### 6.1. Цель оценщика

Оценщик нужен для выбора задач и безопасного резервирования запросов. Он не должен выполнять LLM-вызовы. Прогноз — локальная функция, детерминированная при одинаковых признаках и calibration-файле.

Оценка должна учитывать не только текст задания, но и фактический путь выполнения:

- тип solver;
- выбранная модель;
- длина и язык инструкции;
- число и суммарный размер файлов, которые реально войдут в prompt;
- число доступных инструментов и системных инструкций;
- предполагаемое число итераций/проверок;
- предыдущие фактические расходы solver/model/type в текущем запуске.

Не нужно читать и считать все файлы репозитория, если solver не отправит их модели. В estimator передаётся именно размер потенциального контекста, а не размер всего каталога.

### 6.2. Реализация первой версии

Порядок fallback:

1. **Фактическая медиана по паре `(solver, task_type, model)`**, если имеется достаточное количество валидных наблюдений.
2. **Медиана по `(solver, task_type)`**.
3. **Глобальная медиана по solver/model**.
4. **Простая эвристика по длине prompt и объёму контекста** с консервативным запасом.

Пороговые уровни уверенности:

- `high`: не менее 20 сопоставимых фактических наблюдений;
- `medium`: 8–19 наблюдений;
- `low`: менее 8 наблюдений или fallback на иной тип.

Эти пороги — внутренняя политика команды, а не статистическая гарантия.

### 6.3. Учёт prompt

Считать фактический текст, который отправляется в SDK: system prompt, developer prompt, user instruction, tool descriptions, history и контекст файлов.

Предпочтительный порядок:

1. локальный токенайзер, если его соответствие конкретной модели подтверждено и он может быть включён в образ;
2. коэффициент `chars_per_token`, откалиброванный по usage прокси отдельно по модели и типу содержимого;
3. fallback по медиане фактического input usage для похожих задач.

Нельзя заявлять «ошибка не более 5%» без отдельного измерения на достаточной выборке. Символьный коэффициент различается для русского текста, английского текста, кода, JSON и смешанного контента.

### 6.4. Оценка completion

Не использовать фиксированные значения 40/120/300 как универсальный прогноз. Начальные значения должны браться из реальных трасс для соответствующего solver и формата ответа. Для coding задачи отдельно учитывать повторные циклы, но не использовать неподтверждённые вероятности геометрического распределения.

`upper_cost` — эмпирическая верхняя оценка. При малой выборке она должна быть консервативной, но не описываться как conformal guarantee.

### 6.5. Онлайн-коррекция

После каждого ответа:

- получить фактические `input_tokens` и `output_tokens`;
- вычислить ошибку текущей оценки;
- обновить in-memory множитель для соответствующей модели/solver/type;
- пересчитать оценки ещё не начатых задач;
- записать факты в trace.

Калибровочный файл на диске во время соревнования не переписывать. Обновление текущего запуска не должно менять будущие воспроизводимые эксперименты.

### 6.6. Данные lorne

Использовать существующие трассы как стартовые приоры, но не считать их автоматически эквивалентными финальному соревнованию.

Перед использованием:

- оставить только четыре разрешённые модели или документировать точное сопоставление alias;
- отделить запросы с валидным usage от строк без фактических token counts;
- удалить дубликаты/повторные rollout одной задачи из разных частей split;
- делить train/test по `task_id` или семейству, а не по строкам;
- сравнить распределения prompt, solver, модели и длины трассы с официальными примерами;
- если домены задач различаются, снижать confidence и использовать эти данные только как слабый prior.

Синтетические задачи использовать для тестирования логики estimator/policy и edge cases. Они не становятся обучающими примерами стоимости, пока не пройдены через реальный proxy и не получен usage.

## 7. Определение выполнимости

Нужно различать три состояния:

1. `solvable` — есть поддерживаемый solver или достаточно высокая оценка вероятности решения;
2. `uncertain` — нет доказательства невозможности, но уверенности также недостаточно;
3. `impossible` — есть проверяемое основание, по которому задача не может быть выполнена в данных условиях.

### 7.1. Что разрешено считать доказательством невозможности

- в задаче отсутствует обязательный входной файл/ресурс и регламент не разрешает его получать;
- требования явно противоречат друг другу и это можно показать без догадки;
- формат/путь результата невалиден и не может быть восстановлен из предоставленных данных;
- встроенная проверка или preflight однозначно показывает отсутствие обязательной возможности выполнения.

Одна фраза модели «это невозможно» доказательством не является. Большая оценка стоимости также не означает невозможность.

### 7.2. Политика для uncertain

Не отбрасывать такую задачу автоматически. Для неё вычислить ожидаемую ценность:

`expected_value = reward × P_solve`

Если данных для `P_solve` нет, использовать осторожный prior по solver/type и low confidence. Решение принимается вместе с cost estimate и общим остатком.

### 7.3. Детектирование результата

`solved` устанавливается только после прохождения доступной проверки задачи либо после выполнения подтверждённого формата сдачи, если проверка недоступна. Не помечать задачу решённой только потому, что LLM вернула непустой текст.

## 8. Планировщик: выбор задач при общем бюджете

### 8.1. Основное правило

Поскольку reward известен заранее, а связь reward со сложностью отсутствует, планировщик использует reward как ценность, а не как признак стоимости.

Для каждой задачи строятся:

- `v_i = reward_i × P_solve_i` — ожидаемые баллы;
- `c_i = upper_cost_i` — риск-ориентированная ожидаемая стоимость;
- `t_i` — грубая оценка времени выполнения;
- `status_i` — `solvable`, `uncertain` или `impossible`.

Планировщик выбирает набор задач, максимизирующий `Σ(v_i × x_i)` при ограничениях:

- `Σ(c_i × x_i) <= remaining_budget - planning_reserve`;
- `Σ(t_i × x_i) <= remaining_time`.

`x_i` — 0 или 1. При необходимости использовать дискретизированный knapsack с ограниченным числом состояний. Если полноценный DP не успевает быть реализован и протестирован, fallback — сортировка по `v_i / c_i` с ограничением по остатку бюджета.

### 8.2. Планирование и порядок запуска

1. Прочитать все задачи и rewards до первого LLM-вызова.
2. Исключить доказанно невозможные задачи.
3. Для остальных построить прогнозы стоимости и вероятности решения.
4. Сформировать набор задач под бюджет и время.
5. Внутри выбранного набора начать с наибольшего `v_i / c_i`; при равенстве — с большей абсолютной ожидаемой награды.
6. После каждой задачи обновить фактические статистики и пересчитать план по оставшимся задачам.

Не резервировать весь прогноз задачи как фактический расход. Прогноз используется для планирования; реальный Ledger резервирует и сверяет каждый запрос отдельно.

### 8.3. Резерв планировщика

Ввести один общий `planning_reserve`, чтобы ошибки предварительных прогнозов не съели весь бюджет. Начальное значение — 5% бюджета при наличии приемлемой калибровки; при low-confidence приорах допустимо 10%. Значение уточнить симуляцией на фактических трассах. Это эвристический запас, а не гарантия отсутствия перерасхода.

Не путать `planning_reserve` с резервом конкретного API-вызова в `BudgetLedger`: это два разных уровня защиты.

### 8.4. Выбор модели

Маршрутизация разрешена только между моделями из allowlist. Официальный прогон
идёт с `--model-policy fixed` и базовым алиасом `qwen3.6-35b-a3b`; явный
`LLM_MODEL`/`--model` приоритетен. `metrics` (выбор по измеренному score/cost)
остаётся внутренним экспериментом, а не официальной политикой. Сообщение
организатора 28.10 называет две базовые модели; допустимость `-noreason` —
**confirm with organizers**.

В основной версии выбирать модель на задачу или на шаг по подтверждённым фактическим результатам `(model, solver, task_type)`:

- качество определяется долей успешных решений на отложенных задачах;
- стоимость — фактическим `input/10 + output`;
- сравнивать нужно reward на единицу расхода, а не только средний токеновый расход.

Не выбирать «самую дешёвую» или «самую сильную» модель только по названию. `noreason` включать, если в сравнительном прогоне она сохраняет решаемость и экономит бюджет.

Временный fallback при недостатке статистики — одна модель, прошедшая отборочный smoke-test, для наиболее сложного solver; переключение на другие модели включать после подтверждения совместимости и результатов. Не расходовать бюджет на online-bandit exploration во время основного прогона.

### 8.5. Досрочная остановка

Остановить текущую задачу, если:

- резерв на следующий шаг не проходит проверку Ledger;
- достигнут лимит wall-clock на задачу/всё соревнование;
- несколько последовательных попыток не меняют состояние решения;
- исправление повторяет уже проверенный неудачный патч;
- доступные проверки показывают, что текущая ветка решения не продвигается.

Не останавливать задачу только из-за того, что потрачено больше медианной оценки: перерасход по прогнозу — сигнал пересчитать остаток, а не автоматическое доказательство бесперспективности.

## 9. Решатели

### 9.1. Общий интерфейс

```python
class Solver(Protocol):
    def supports(self, task: Task) -> bool: ...
    async def solve(self, task: Task, context: SolverContext) -> SolveResult: ...
```

`SolverContext` содержит `OpenJiuwenGateway`, `BudgetLedger`, рабочий каталог задачи, лимиты времени, `CostEstimator` и logger. Solver не должен иметь независимый экземпляр LLM-клиента.

### 9.2. Детерминированный solver

- Использовать только для типов/паттернов, которые действительно покрыты проверенной логикой.
- Проверить формат и граничные случаи на исходных примерах.
- Если вход не соответствует ожидаемому шаблону, передать задачу в следующий solver, а не возвращать уверенно неверный ответ.
- Нулевой расход допустим только при отсутствии любых LLM-вызовов и подтверждённом корректном ответе.

Локальный результат `8/8, 0 токенов`, указанный в v4.0, не является основанием считать все задачи финального набора детерминированными.

### 9.3. Coding solver

Минимальный безопасный цикл:

1. прочитать инструкцию, целевые файлы и доступные проверки;
2. получить план изменения;
3. запросить минимальный патч;
4. применить патч только при однозначном совпадении контекста;
5. выполнить синтаксическую проверку и относящиеся к задаче тесты;
6. при ошибке передать модели точную первую диагностическую ошибку и компактный контекст;
7. повторить в пределах установленного лимита;
8. после успешной проверки сохранить требуемый ответ.

Для SEARCH/REPLACE использовать последовательность:

- точное совпадение;
- совпадение после нормализации пробелов/переводов строк;
- нормализация отступов;
- AST-якорь для структур кода, если он уже реализован;
- fuzzy match только при одном однозначном кандидате с высоким порогом сходства.

Если найдено 0 совпадений или больше 1 подходящего совпадения, патч не применять. Вернуть модели короткий `closest_window` и запросить уточнённый diff. Не перезаписывать целый файл, если задачу можно решить локальным патчем.

Тестовые файлы защищены: сохранить их хеши до первого изменения; запрещать solver менять проверяющие файлы, если они выделены в структуре задачи; после попытки восстановить случайно изменённые тесты и повторно проверить хеши. Нельзя принимать решение как успешное, если тесты были подменены.

В пределах двухдневного срока не реализовывать best-of-two и retrieval-память, если базовый цикл не прошёл все тесты. Стартовый максимум итераций — 3; менять его только по фактическим трассам.

### 9.4. Универсальный solver

- Работает с неизвестным `task_type` и не ломает весь процесс.
- Читает фактическую инструкцию и релевантные файлы задачи.
- Не требует JSON-ответа, если задача явно не просит JSON.
- Учитывает формат ответа из `task.json`/инструкции.
- Делает один ограниченный вызов, затем при необходимости — только одну дополнительную попытку форматирования, если её резерв проходит через Ledger.
- Возвращает явный статус и причину ошибки.

Если структура задачи не распознана, сохранять raw `task.json` в контексте диагностики и не терять неизвестные поля при адаптации.

## 10. Сохранение ответов и файловая система

### 10.1. Обязательный путь

Для задачи `<TASKS>/<task_id>/` файл ответа:

`<TASKS>/<task_id>/answer.txt`

Не использовать `OUT` вместо этого пути, пока организаторы явно не подтвердят другое. Пример команды запуска монтирует `$TASKS` в `/data/tasks:rw`, но не показывает монтирование `$OUT`.

### 10.2. Запись

Запись выполнять атомарно на том же mount:

1. создать временный файл в каталоге задачи;
2. записать ответ в UTF-8;
3. выполнить `flush()` и `os.fsync()`;
4. выполнить `os.replace(temp_path, answer_path)`;
5. при необходимости выполнить `fsync` каталога;
6. убедиться, что `answer.txt` существует и содержит ожидаемый текст.

После каждого успешно проверенного решения сразу сохранить `answer.txt`. Не держать все ответы только в памяти до конца прогона.

Регламент требует создать `answer.txt` в каждой папке задачи. Поэтому на старте создать пустой файл там, где его ещё нет, а после решения заменить его содержимым. Пустой файл не считается решённой задачей и не должен попадать в `solved_count`.

### 10.3. Диагностика

`predictions.jsonl` и `trace.jsonl` не требуются регламентом как сдаваемые файлы, а путь `OUT` в примере запуска неоднозначен. Для отладки:

- писать структурированные диагностические строки в `stderr`;
- временные подробные трассы хранить в `/tmp`;
- если организаторы подтвердят смонтированный `OUT`, сохранять туда `predictions.jsonl` и `trace.jsonl`;
- не создавать служебные файлы в каталоге задачи, кроме требуемого `answer.txt`, без необходимости.

## 11. Runtime, Docker и безопасность

### 11.1. Обязательные ограничения

- общий runtime — не более 1 часа;
- не более 5 одновременных сессий;
- CPU — официально разрешено 8 логических ядер; локальные тесты используют 4 CPU консервативно;
- RAM — не более 16 ГБ;
- без GPU и локальных нейросетевых моделей;
- образ — менее 4 ГБ по указанной организаторами команде `docker images`;
- сборка — менее 1000 секунд;
- после сборки ничего не скачивать и не устанавливать;
- LLM-трафик — только через заданный proxy.

### 11.2. Контейнер

Ожидаемый запуск, приведённый в регламенте, использует:

- `--network hack-net`;
- `--read-only`;
- `--tmpfs /tmp:rw,size=2g`;
- `HOME=/tmp`;
- `--cap-drop ALL`;
- `--security-opt no-new-privileges`;
- bind mount `$TASKS:/data/tasks:rw`;
- `python /app/run_agent.py --tasks-dir /data/tasks`.

Финальный локальный тест должен воспроизводить фактическую команду, включая mount permissions. Нельзя считать тест `docker run` успешным, если он запускался с более широкими правами или дополнительными volume, которых не будет у жюри.

Проверить права на запись в каталог задачи при фактическом пользователе процесса. Не добавлять `USER` с непривилегированным UID без проверки bind mount: каталог на хосте может оказаться недоступен этому UID. При этом не ослаблять ограничения Docker и не добавлять capabilities ради удобства.

### 11.3. Сборка

- Зафиксировать базовый image не только тегом, но и digest.
- Закрепить `openjiuwen` и транзитивные зависимости через lock-файл (`uv.lock` или requirements lock с хешами).
- Не использовать `pip install -U` в финальной сборке.
- Не устанавливать WorkSwarm, браузерные инструменты, базы данных и дополнительные UI-компоненты, если они не нужны решателю.
- Использовать `--no-cache-dir`, удалить build cache и временные артефакты из runtime image.
- Не включать в образ датасеты, локальные логи, `.git`, ключи и любые веса нейросетей.
- Проверить размер командой организаторов; целевой внутренний размер — с запасом относительно 4 ГБ.

### 11.4. Секреты и сеть

- `LLM_API_KEY` передаётся только через env при запуске.
- Не записывать ключ в логи, calibration JSON, trace или README.
- Не скачивать модели, пакеты, датасеты или дополнительные ресурсы при запуске.
- Запретить все сетевые вызовы, кроме запросов к `LLM_BASE_URL`; проверить это отдельно для estimator и всего runtime.
- Не использовать сеть в тестах estimator.
- Отключить telemetry/обновления SDK, если они инициируют внешние соединения и не нужны для решения.

## 12. Эксперименты и критерии выбора реализации

### 12.1. Что тестировать в первую очередь

1. Исходный harness без изменений — baseline.
2. Оценщик по типу и фактическим медианам.
3. Оценщик с признаками prompt/файлов.
4. Риск-ориентированная политика выбора задач.
5. Обновление оценки после каждого LLM-вызова.
6. Выбор модели по фактической решаемости и стоимости.
7. Эффект детерминированных решателей и coding patch loop.

### 12.2. Что не включать в основную версию без доказательства выигрыша

- LLM self-estimate (T8);
- model probe (T16);
- online bandit (T11);
- best-of-two (T17);
- память успешных эпизодов (T18);
- нейросетевой оценщик до 5 МБ;
- отдельная сложная модель геометрического распределения числа попыток;
- полноценный conformal predictor по каждому типу при малом количестве наблюдений.

Эти элементы не запрещены, но при текущем сроке имеют низкий приоритет и могут ухудшить score за счёт дополнительных вызовов, сложности интеграции и регрессионного риска.

### 12.3. Данные и split

- 8 официальных примеров — smoke test формата, не репрезентативная обучающая выборка.
- 20 задач lorne — полезный второй полигон, если структура и типы сопоставимы.
- 620 строк бенчмарка использовать только после проверки качества usage, идентификаторов моделей и отсутствия утечек.
- Синтетика — unit/integration tests и stress tests; не выдавать её за реальные расходы.
- Train/test разделять по задаче/семейству. Не использовать результаты одного task_id в обеих частях.
- Сохранить фиксированный seed и версии датасетов.

### 12.4. Метрики

| Метрика | Определение | Для чего |
|---|---|---|
| TotalScore | сумма reward за успешно проверенные задачи | Главный результат |
| Solve rate | успешно решённые / все задачи | Контроль качества |
| Cost per solved | суммарная стоимость / успешно решённые задачи | Экономичность |
| MAE | средняя абсолютная ошибка прогноза стоимости | Базовая точность estimator |
| MdAPE | медианная абсолютная процентная ошибка | Устойчивость к выбросам |
| WAPE | `Σ|y-ŷ| / Σy` для `Σy > 0` | Ошибка на общем расходе |
| Underestimate@upper | доля случаев, когда факт превысил upper estimate | Риск недооценки |
| Budget violation | число запросов, начатых без достаточного резерва | Должно быть 0 локально |
| Wall time | общее время процесса и время на задачу | Укладываемся в 1 час |

MAPE считать только на положительных расходах. Для нулевых расходов показывать отдельную долю задач с нулевым расходом.

### 12.5. Бюджетные сценарии

Не использовать 20k/50k/100k как официальные бюджеты, пока организаторы не подтвердили эти значения. Для локальной симуляции можно построить несколько сценариев, но в отчёте пометить их как synthetic budget scenarios. Главный сценарий должен соответствовать реальному бюджету соревнования.

### 12.6. Принцип принятия улучшения

Новая реализация включается по умолчанию, если одновременно:

- проходит все unit/contract tests;
- не ухудшает отборочный прогон;
- не создаёт дополнительных неконтролируемых LLM-вызовов;
- не нарушает бюджетный инвариант;
- показывает лучший или не худший TotalScore на отложенных задачах при сопоставимом бюджете;
- укладывается в runtime, RAM, CPU и размер образа.

Если данных недостаточно, оставить простую базовую реализацию. Не включать сложную теорию только потому, что она математически привлекательна.

## 15. Тесты и матрица приёмки

### 15.1. Unit tests

- чтение reward и task directory;
- неизвестные дополнительные поля `task.json`;
- расчёт `input/10 + output`;
- отсутствие двойного учёта reasoning;
- нормализация всех поддерживаемых usage formats;
- atomic answer write;
- ledger reserve/settle/release;
- два одновременных запроса, конкурирующих за остаток;
- отсутствие запроса при недостаточном резерве;
- deterministic solver fallback;
- unknown task type → generic solver;
- impossible vs uncertain;
- патч с 0/1/>1 совпадениями;
- защита тестовых файлов;
- остановка по времени.

### 15.2. Интеграционные тесты

1. Fake OpenJiuwen gateway: 100 задач, фиксированный бюджет, известные usage и ответы.
2. OpenJiuwen SDK → proxy: короткий запрос, разрешённая модель, usage fixture.
3. Один полный путь: loader → planner → reserve → SDK call → settle → checker → `answer.txt`.
4. Обрыв соединения после отправки: резерв не возвращается без доказательства, что запрос не дошёл.
5. Достижение бюджета: следующие вызовы не отправляются.
6. Достижение wall-clock: новые задачи не стартуют, уже сохранённые ответы остаются на месте.

### 15.3. Финальный Docker test

Запустить максимально близко к команде жюри:

```bash
mkdir -p "$OUT" && chmod 777 "$OUT"

docker build -t "hack:latest" .

timeout -k 1000s 1h docker run --rm --name "run-${TEAM}" \
  --network hack-net \
  -e LLM_BASE_URL -e LLM_API_KEY \
  -e BUDGET \
  -v "$TASKS:/data/tasks:rw" \
  --read-only --tmpfs /tmp:rw,size=2g -e HOME=/tmp \
  --cap-drop ALL --security-opt no-new-privileges \
  --cpus 4 --memory 16g --pids-limit 512 \
  --workdir /app --entrypoint python \
  hack:latest /app/run_agent.py --tasks-dir /data/tasks
```

`--cpus 4` в локальном тесте — консервативное значение; официально разрешено 8 логических ядер, но 4 достаточно для проверки. `-e BUDGET` обязателен: бюджет официально передаётся в `BUDGET` и может отличаться от 100k; `OJ_TOKEN_BUDGET` поддерживается, но не является официальным именем. Не передавать контейнеру дополнительные volume или права, отсутствующие в официальной команде.

## 17. Жёсткие правила для разработчиков и AI Coding Agent

При выполнении задач разработчик или coding agent обязан:

1. Перед изменением прочитать целевой модуль, вызывающий код, типы и связанные тесты.
2. Не менять API/CLI и структуру task format на основании догадки.
3. Сначала добавить тест на конкретный дефект, затем менять реализацию.
4. Не переписывать файлы целиком, если достаточно локального изменения.
5. Не добавлять новую зависимость без оценки размера Docker image и времени сборки.
6. Не запускать сетевые LLM-запросы из estimator, planner, unit tests или offline mode.
7. Не обращаться к моделям вне списка организаторов.
8. Не создавать вторые независимые счётчики токенов.
9. Не обходить `BudgetLedger` прямым вызовом SDK.
10. Не считать задачу решённой по одному лишь ответу модели.
11. Не модифицировать проверяющие тесты и не оставлять их изменёнными после solver run.
12. Не выполнять рискованный рефакторинг перед freeze.
13. После изменения запускать минимум целевые тесты, затем полный набор.
14. В отчёте указывать фактическую команду, exit code и результат. Не заявлять прохождение непроверенного теста.
15. При блокере после двух коротких попыток зафиксировать причину и перейти к независимой задаче; не тратить полдня на неподтверждённую теорию.

### Приоритет, если времени не хватает

1. OpenJiuwen + proxy + task input/output contract.
2. BudgetLedger и правильный usage accounting.
3. Сохранение `answer.txt` и отборочный прогон.
4. Стабильные solver paths и unknown-type fallback.
5. Простой estimator и planner по reward/cost.
6. Дополнительные оптимизации, статистика и эксперименты.

Пункты 1–4 нельзя обменивать на новые теории оценивания стоимости.

## 18. Справочные источники и практические основания

Ссылки проверены 10 ноября 2026. При расхождении между текущей документацией и закреплённой версией SDK приоритет имеет поведение закреплённой версии, проверенное тестом.

1. **Регламент openJiuwen Challenge 2026** — предоставленный командой документ соревнования. Имеет высший приоритет для лимитов, формата сдачи, моделей и критериев оценки.
2. **openJiuwen Agent Core — официальный GitHub:** <https://github.com/openJiuwen-ai/agent-core>. Репозиторий описывает Core как Python SDK для создания Agent, orchestration, model invocation, tools, runtime и observability. В Quick Start приведены `ModelClientConfig`, `ModelRequestConfig`, `WorkflowAgent`, `LLMComponent` и `Runner.run_agent`.
3. **openJiuwen Core 0.1.20.post1 — PyPI:** <https://pypi.org/project/openjiuwen/0.1.20.post1/>. На дату проверки релиз опубликован 3 ноября 2026; указан Python `>=3.11,<3.14`. SDK нужно закрепить, транзитивные зависимости — lock-файлом.
4. **openJiuwen — официальный сайт и документация:** <https://openjiuwen.com/en/> и <https://openjiuwen.com/en/docs-page>. Сайт разделяет Agent Core, Agent Runtime, Agent Studio и WorkSwarm; для данной задачи нужен Core SDK, если организаторы не потребуют иного.
5. **BAGEN — Towards Budget-Aware Agents:** <https://github.com/mll-lab-nu/BAGEN> и <https://ragen-ai.github.io/bagen/>. Практически релевантная идея: оценивать остаточный ресурс по мере выполнения, а не только после завершения. Репозиторий ориентирован на budget estimation по rollout prefixes, в том числе для coding traces.
6. **Google Research — Budget-Aware Tool-Use / BATS:** <https://github.com/google-research/budget-aware-agent>. Полезные идеи: постоянно показывать агенту остаток бюджета, делать early stopping, сохранять промежуточные результаты и выбирать продолжение с учётом стоимости.
7. **JiuwenSwarm / WorkSwarm:** <https://github.com/openJiuwen-ai/jiuwenswarm>. Это отдельное прикладное приложение на базе openJiuwen; его установка и зависимости не нужны для минимального конкурсного harness, если организаторы прямо не требуют именно Swarm.
