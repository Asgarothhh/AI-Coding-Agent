## 2. Задача простыми словами

Мы сдаём агента, который запускается в контейнере без интернета, получает каталог задач и общий бюджет в токенах. По каждой задаче он пишет одну строку ответа в `answer.txt`.

Оценивается три вещи:

1. **Точность прогноза.** До решения агент говорит, сколько токенов потратит. Чем ближе прогноз к факту, тем лучше.
2. **Дисциплина бюджета.** Агент не имеет права выйти за лимит: лучше пропустить задачу, чем сжечь бюджет впустую.
3. **Качество ответов.** Больше решённых задач и больше очков на единицу потраченного бюджета.

Отсюда три числа, которые оптимизируем: MAPE прогноза, число перерасходов (должно быть 0) и score при бюджетах 20k / 50k / 100k.

## 4. Теории, которые проверяем

Принцип: факты собираем **один раз**, дальше все статические теории считаются офлайн и бесплатно. Живые вызовы — только там, где теория без них не проверяется (T8, T11, T16).

### T1. Приор по типу задачи
**Идея.** Стоимость в основном определяется типом задачи, а не текстом инструкции.
**Формула.** `ŷ = медиана(y | type)`, интервал `[q10, q90]` по тому же типу; уверенность: высокая при n ≥ 20, средняя при n ≥ 8, иначе низкая.
**Где.** `harness/estimator.py::TypePrior`.
**Проверка.** MAPE на отложенной выборке; сравнение с константой B0.
**Отказ.** Если MAPE ≤ 20%, сложные модели не добавляем.
**Задача.** T002. **Токены.** 0.

### T2. Учёт токенов промпта
**Идея.** Стоимость в основном состоит из промпта, а промпт известен заранее.
**Формула.** `ŷ = prompt_tokens/10 + completion_estimate`, где `prompt_tokens = tokenizer(текст)` или `len(текст)/ratio`; `completion_estimate` = 40 для короткого ответа, 120 для JSON-патча, 300 для объяснения.
**Где.** `harness/estimator.py::PromptAccounting`.
**Проверка.** На 8 примерах сравнить с фактическим `prompt_tokens`; ошибка ≤ 10% для 7 из 8 задач.
**Отказ.** Если токенайзера нет офлайн — используем `ratio` из T13.
**Задача.** T008. **Токены.** 0.

### T3. Степенная зависимость
**Идея.** Чем длиннее инструкция и больше файлов, тем дороже, но рост замедляется.
**Формула.** `log y = b0 + b1·log(1+instr_chars) + b2·log(1+files) + b3·log(1+kb_bytes) + type`, обучение ridge-регрессией, α по кросс-валидации, прогноз через `exp`.
**Где.** `harness/estimator.py::LogLinear`.
**Проверка.** R² ≥ 0,5; доверительный интервал для b1; сравнение с T1 на отложенной выборке.
**Отказ.** Если не лучше T1 — выкидываем.
**Задача.** T008. **Токены.** 0.

### T4. Модель цикла починки тестов
**Идея.** Починка — это серия попыток; число попыток случайно и зависит от класса ошибки.
**Формула.** `N ~ Geometric(p)`: p = 0,6 для синтаксиса, 0,35 для падения assert, 0,2 для логики; при mutation-repair p += 0,15. Стоимость = сумма `(prompt_k/10 + completion_k)` по k = 1..N, `prompt_k = base + k·growth`, обрезаем по `max_iterations=6`. Прогноз — медиана и q80.
**Где.** `harness/estimator.py::RepairHazard`.
**Проверка.** Медиана итераций ±1; q80 покрывает ≥ 60% фактов.
**Отказ.** Если покрытие ниже 60% — оставляем только медиану.
**Задача.** T008. **Токены.** 0.

### T5. Онлайн-обновление прогноза
**Идея.** После каждого фактического вызова прогноз остатка нужно пересчитывать, а не ждать конца.
**Формула.** Множитель `m` имеет логнормальный приор по типу; после k наблюдений posterior обновляется, `ŷ_total = spent + m̂·base·(1 + 0,5·(k−1))`.
**Где.** `harness/estimator.py::OnlineUpdate`.
**Проверка.** Ошибка прогноза остатка падает ≥ 15% против статичной калибровки.
**Отказ.** Если выигрыш < 5% — убираем.
**Задача.** T008. **Токены.** 0.

### T6. Конформные интервалы
**Идея.** Нужна статистическая гарантия, что прогноз не занижен, иначе бюджет будет пробит.
**Формула.** На калибровке считаем остатки `r = y/ŷ`, берём квантили q10 и q90, интервал `[ŷ·q10, ŷ·q90]`; верхняя граница используется в политике.
**Где.** `harness/estimator.py::Conformal`.
**Проверка.** PICP@90 ≥ 0,85; средняя ширина ≤ 2·ŷ.
**Отказ.** Если покрытие < 75% — только точечный прогноз, политика берёт запас 50%.
**Задача.** T008. **Токены.** 0.

### T7. Экономика принять/отклонить
**Идея.** Бюджет — дефицитный ресурс, у него есть теневая цена.
**Формула.** `λ` — теневая цена единицы бюджета, подбирается на калибровке; принимаем задачу, если `reward·P_solve − λ·E[cost] > 0` и `upper_bound + reserve ≤ remaining`. Иначе `reject:cost`.
**Где.** `harness/policy.py::CostSensitive`.
**Проверка.** Score при 20k выше, чем у политики «берём всё», на ≥ 15%; перерасходов 0.
**Отказ.** Если при 50k хуже базовой политики — откат к порогу по верхней границе.
**Задача.** T003. **Токены.** 0.

### T8. Самооценка моделью
**Идея.** Модель может знать, сколько токенов ей понадобится.
**Формула.** Один вызов с промптом «Оцени число токенов на решение, ответь JSON `{estimate, confidence}`»; стоимость вызова включается в бюджет эксперимента.
**Где.** `harness/estimator.py::SelfEstimate`.
**Проверка.** MAPE меньше 1,5 от лучшей эвристики.
**Отказ.** Если вызов дороже выигрыша — теория отклонена, результат фиксируем в README.
**Задача.** T008. **Токены.** около 60 на задачу.

### T9. Похожие задачи стоят похоже
**Идея.** Ближайшие соседи по тексту инструкции дают хороший прогноз.
**Формула.** TF-IDF по символьным n-граммам 3–5, k = 5, прогноз — медиана соседей; только стандартная библиотека.
**Где.** `harness/estimator.py::KNN`.
**Проверка.** MAPE не хуже T1 при 100+ задачах.
**Отказ.** Если на синтетике выигрыша нет — выкидываем.
**Задача.** T008. **Токены.** 0.

### T10. Оптимальная остановка
**Идея.** Продолжать имеет смысл, только пока ожидаемая выгода больше ожидаемой стоимости.
**Формула.** Останавливаемся, если posterior `P(y > cap | spent) > 0,5` или `E[остаток reward] < λ·E[остаток cost]`; реализация — последовательный критерий с порогом.
**Где.** `harness/policy.py::ShouldStop`.
**Проверка.** Минус 30% безнадёжных прогонов при потере решаемости ≤ 5%.
**Отказ.** Если теряем больше 10% решаемости — только жёсткий лимит итераций.
**Задача.** T003. **Токены.** 0.

### T11. Бандит на выбор модели
**Идея.** Дешёвая и дорогая модели дают разное качество за разную цену.
**Формула.** Thompson sampling по Beta-постерам для пары {дешёвая, сильная}; награда — score на единицу стоимости.
**Где.** `harness/policy.py::BanditRouter`.
**Проверка.** Минус 20% стоимости при том же score.
**Отказ.** Если менять модель на каждом вызове нельзя — теория условная, по умолчанию выключена.
**Задача.** T003. **Токены.** зависят от числа проб.

### T12. Абляция признаков
**Идея.** Нужно знать, какие признаки реально несут сигнал, а не гадать.
**Формула.** Leave-one-feature-out и permutation importance, 200 повторов; отчёт по приросту MAPE.
**Где.** `eval/metrics.py::feature_ablation`.
**Проверка.** Таблица важности в `results.md`.
**Отказ.** Нет; это протокол исследования.
**Задача.** T009. **Токены.** 0.

### T13. Калибровка «символы в токены»
**Идея.** Реальный токенайзер не всегда доступен, но коэффициент можно измерить.
**Формула.** EMA отношения `chars/tokens` по каждой модели; ограничение 1,2–4,5; игнорируем выборки меньше 32 токенов и 32 символов; фолбэк по семейству модели.
**Где.** `harness/estimator.py::CharsPerToken` (в памяти, без записи на диск).
**Проверка.** Ошибка прогноза промпта ≤ 5%.
**Отказ.** Если > 15% — используем только настоящий токенайзер.
**Задача.** T002. **Токены.** 0.

### T14. Патч через поиск и замену
**Идея.** Перезапись всего файла — дорогой и хрупкий способ; замена фрагмента дешевле и надёжнее.
**Формула.** Модель возвращает блоки SEARCH/REPLACE. Применяем по лестнице: точное совпадение → обрезка пробелов → нормализация отступов → кавычки и переводы строк → якорь по AST → сходство ≥ 0,92. Требуем уникальность; при промахе возвращаем `closest_window` как подсказку.
**Где.** `harness/patch.py`.
**Проверка.** Доля успешных применений на 20 задачах lorne; расход completion падает на ≥ 40%; решаемость +10 п.п.
**Отказ.** Если нет выигрыша по score и стоимости — оставляем текущий способ.
**Задача.** T005. **Токены.** 0.

### T15. Петля проверки с возвратом ошибки
**Идея.** Модель чинит быстрее, если видит точную ошибку, а не пересказ.
**Формула.** После правки: синтаксис → линтер (если установлен) → связанные тесты. Первая строка `FAILED` дословно идёт в следующий промпт. Максимум 6 итераций. Хеши тестовых файлов неизменны, изменённые восстанавливаются.
**Где.** `harness/solvers/coding.py`.
**Проверка.** +15 п.п. решаемости на coding при росте стоимости ≤ 25%.
**Отказ.** Если стоимость выросла сильнее — оставляем 3 итерации.
**Задача.** T006. **Токены.** 0 (стоимость самого решения).

### T16. Проба модели даёт вероятность решения
**Идея.** Сила модели на задаче предсказуема по маленькой пробе.
**Формула.** 8 микропроб один раз на модель, `repeats=1`; профиль переводится в `P_solve` по типу задачи.
**Где.** `harness/policy.py::ProbePrior`, запуск `eval/probe.py`.
**Проверка.** Ошибка вероятности ≤ 0,15 на отложенной выборке.
**Отказ.** Если хуже константы 0,5 — не используем.
**Задача.** T003. **Токены.** 8 вызовов один раз.

### T17. Два варианта правки
**Идея.** Разные температуры дают разные патчи; иногда второй проходит, когда первый нет.
**Формула.** Два прогона при T = 0,2 и 0,6; применяем оба, побеждает меньший проходящий дифф; стоимость ≤ 2×.
**Где.** `harness/solvers/coding.py::best_of_two`.
**Проверка.** Score на единицу стоимости растёт.
**Отказ.** Если выигрыш ≤ 5% — выключаем.
**Задача.** T006. **Токены.** до 2× на решение.

### T18. Память успешных эпизодов
**Идея.** Удачный патч для похожей ошибки стоит показать модели как пример.
**Формула.** Храним `(type, error_class, patch)` в JSON; достаём top-3 по сходству; лимит 800 токенов на пример.
**Где.** `harness/memory.py`.
**Проверка.** +5 п.п. решаемости при росте стоимости ≤ 20%.
**Отказ.** Если дороже — выключаем.
**Задача.** T006. **Токены.** 0.

### T19. Приоры из бенчмарка lorne
**Идея.** 620 реальных прогонов дают готовые медианы до начала калибровки.
**Формула.** Из валидных 326 строк берём медианы `tokens_in`, `tokens_out`, `steps` по паре (модель, тип); используем как B1-приор и приор для T5.
**Где.** `eval/priors.py`, попадает в `harness/calibration.json`.
**Проверка.** Лучше равномерного бейзлайна.
**Отказ.** Если не лучше T1 — не используем.
**Задача.** T002. **Токены.** 0.

## 5. Требования к системе

| ID | Требование |
|---|---|
| ТР-01 | Когда задача попадает в план, система выдаёт прогноз: число, интервал, уверенность и список факторов |
| ТР-02 | Система пишет `predictions.jsonl` с полями: задача, тип, признаки, прогноз, интервал, уверенность, теория, версия модели, время |
| ТР-03 | Калибровка считается только на обучающей части и коммитится в `harness/calibration.json` |
| ТР-04 | Когда приходит фактический `usage`, система обновляет прогноз остатка и сохраняет потраченное и новый прогноз |
| ТР-05 | Если верхняя граница прогноза превышает лимит задачи или остаток бюджета, задача останавливается с причиной в трейсе |
| ТР-06 | При планировании каждая задача получает явный вердикт: принять, отклонить из-за стоимости, отклонить как невыполнимую, отклонить из-за времени |
| ТР-07 | Если тип задачи неизвестен, работает универсальный солвер: один вызов LLM и извлечение ответа |
| ТР-08 | Прогноз детерминирован при одинаковых входах и seed |
| ТР-09 | Прогноз не делает сетевых вызовов |
| ТР-10 | Стоимость считается как `prompt/10 + completion`; reasoning входит в completion и не считается дважды |
| ТР-11 | Ответ пишется атомарно (fsync и os.replace) и только при успехе |
| ТР-12 | Детерминированные типы решаются без LLM, если проверка на выполнимость ниже порога |
| ТР-13 | В stdout один JSON-объект; диагностика идёт в stderr |
| ТР-14 | Контейнер работает при read-only rootfs, `HOME=/tmp`, без сети кроме прокси |
| ТР-15 | В `trace.jsonl` есть прогноз, факт и идентификатор теории — для последующей проверки |
| ТР-16 | При правке кода хеши тестовых файлов сохраняются; изменённый тест восстанавливается до того, как солвер сдастся |
| ТР-17 | Оценщик, политика и солверы подключаются через реестр; замена реализации не меняет вызывающий код |
| ТР-18 | Нейросетевой оценщик работает офлайн, весит не больше 5 МБ; при любой ошибке — откат на эвристику с записью в stderr |
| ТР-19 | Выбор реализаций задаётся переменными `OJ_ESTIMATOR`, `OJ_POLICY`, `OJ_SOLVER`; значения по умолчанию — калиброванные эвристики |
| ТР-20 | Runtime обязан использовать openJiuwen SDK: выбор бэкенда фиксируется в stderr и в поле `llm_backend` итогового JSON |
| ТР-21 | Доказательство использования openJiuwen: версия пакета, строка `LLM backend: openjiuwen`, `llm_backend` в summary и harness-отчёт |
| ТР-22 | DeepAgent подключается к раннеру только при измеримом выигрыше по score или стоимости; иначе фиксируется отказ |

**Нефункциональные требования:** прогноз не дольше 50 мс на задачу; образ не больше 4 ГБ (сейчас 1,39 ГБ); холодная сборка не дольше 5 минут; полный прогон не дольше часа; тесты детерминированы и работают без сети.

## 8. Как проводим эксперименты

**Данные.** 8 официальных примеров — только для дымового прогона. 40–60 синтетических задач (по 10 на тип, seed 42). 16–18 задач из lorne — второй отложенный набор. Факты собираем один раз в `eval/results/ground_truth.jsonl`. Разбиение 70/30, калибровка только на обучающей части.

**Метрики.**

- MAPE — средняя относительная ошибка прогноза.
- MdAPE — медианная относительная ошибка, устойчива к выбросам.
- Смещение — среднее отношение прогноза к факту; идеал 1,0.
- Pinball — качество квантильных прогнозов.
- PICP@90 — доля фактов, попавших в 90% интервал.
- MPIW — средняя ширина интервала.
- Перерасход — сколько раз факт превысил лимит; цель 0.
- Score при 20k / 50k / 100k — очки в симуляции бюджета.
- Сожаление решения — сколько очков потеряли из-за неверного принять/отклонить.
- Задержка прогноза.

**Бейзлайны.** B0 — константа 1000 единиц. B1 — медиана по типу. B2 — текущая эвристика. B3 — калиброванная T2+T3. B4 — победитель на отложенной выборке.

**Статистика.** Bootstrap на 2000 пересэмплирований для доверительных интервалов метрик; парный критерий Уилкоксона по ошибкам задач; при малом числе задач приводим медианы и межквартильный размах. Гипотезы и критерии отказа фиксируем до прогонов.

**Волны и бюджет экспериментов (жёсткий стоп 150k единиц).**

| Волна | Когда | Что делаем | Бюджет |
|---|---|---|---|
| В0 | день 0 | факты по 8 примерам, проверка токенайзера, T1, T13 | около 10k |
| В1 | день 1 | синтетика и факты, T2, T3, T4, T9, офлайн-проверка T14 и T15 | около 70k |
| В2 | день 2 | T5, T6, T7, T10, абляции, симуляции 20/50/100k, T19 | около 40k |
| В3 | день 2–3, если остаток | T8, T17, T11 только при разрешении организаторов | не больше 30k |

**Гейты.** Г1 после В0: есть ли токенайзер офлайн. Если да — T2 становится основной, если нет — считаем символы с замеренным коэффициентом. Г2 после В1: если T1 даёт MAPE ≤ 20%, замораживаем простую модель. Г3 после В2: выбираем модель по ошибке на отложенной выборке при покрытии интервала не ниже 85% и нуле перерасходов; проверяем, что score при 20k не хуже бейзлайна. Г4: теория, не прошедшая критерий отказа, попадает в README как отрицательный результат.

## 12. Порядок действий для агента-исполнителя

### 12.1. Подготовка

1. Прочитать разделы 0, 5, 6, 10, 11, 12 полностью.

4. Убедиться, что базовые 113 + 29 тестов зелёные. Если нет — остановиться и зафиксировать проблему, дальше не идти.

### 12.2. Цикл выполнения одной задачи

1. Взять задачу из `tasks.yaml` с выполненными зависимостями.
2. Прочитать её `accept` и файлы, которые она затрагивает.
3. Сначала написать тест (или расширить существующий), потом реализацию.
4. Запустить локальные команды задачи.
5. Если проверки не проходят — исправить и повторить, максимум 3 попытки.
6. После 3 неудач: откатить изменения задачи, пометить её `blocked` в отчёте, перейти к независимой задаче.
7. Закоммитить одной строкой: `T00X: <что сделано>`.
8. Записать в `eval/results/progress.md`: задача, команда, результат, потраченные токены.

### 12.4. Правила коммитов

- Один коммит — одна задача.
- Заголовок `T00X: ...`, тело — команды проверки и результат.
- Не коммитить `team.json`, ключи, `eval/results/*.jsonl` с персональными данными.
- Не менять чужие лейны и не переписывать существующие тесты.

### 12.5. Условия остановки

- 3 неудачные попытки по задаче → откат и пометка `blocked`.
- Сумма токенов экспериментов превысила 150k → прекратить живые прогоны, работать на записанных фактах.
- Наступило 12 ноября 18:00 MSK → заморозка, только T013.
- Появился секрет в диффе → остановиться и вычистить.
- Тесты базовой линии сломались → остановиться, чинить сначала их.

### 12.6. Как вставить нейросетевой оценщик

Оценщик подключается через реестр и не меняет вызывающий код.

```python
# harness/estimator.py
class NeuralEstimator:
    def __init__(self, weights: Path) -> None: ...
    def predict(self, task: Task) -> Estimate: ...
    def update(self, task: Task, spent: float, attempt: int,
               error: str | None) -> Estimate: ...

# harness/registry.py
def build_estimator(name: str | None = None) -> TokenEstimator:
    name = name or os.environ.get("OJ_ESTIMATOR", "calibrated")
    ...
```

Требования к нейросетевой реализации:

- веса лежат в репозитории, не больше 5 МБ, без скачивания;
- `predict` не делает сетевых вызовов и укладывается в 50 мс;
- результат детерминирован при одном и том же входе;
- любое исключение перехватывается и заменяется результатом эвристики, причина уходит в stderr;
- контрактные тесты те же, что для эвристики, плюс тест на откат при битых весах.

Порядок включения: реализовать класс → зарегистрировать имя `neural` → добавить тесты → прогнать контракт → поставить `OJ_ESTIMATOR=neural` в эксперименте → сравнить с B3 на отложенной выборке → включить по умолчанию только при выигрыше.
