# AGENTS.md — правила работы агентов в репозитории

## Проект и цель

openJiuwen Challenge 2026: batch-агент `Stevenson 1.0`, который решает пакет задач
в рамках одного общего бюджета токенов. Цель — максимизировать сумму `reward` за
правильно решённые задачи при ограниченном бюджете, а не точность прогноза
стоимости. Прогноз — только инструмент выбора задач и безопасного резервирования.

Обязательный артефакт каждой задачи — `<TASKS>/<task_id>/answer.txt`. Пустой файл
не считается решением. Стек: Python 3.11, stdlib-only ядро,
`openjiuwen==0.1.20.post1` (openJiuwen Core SDK), 4 CPU, 16 ГБ RAM, контейнер не
более 1 часа, образ менее 4 ГБ, read-only rootfs, `HOME=/tmp`, сеть только до
LLM-прокси. Точка входа: `python run_agent.py --tasks-dir /data/tasks`.

Формула стоимости: `output_tokens + input_tokens / 10`; reasoning входит в выходной
расход и не должен учитываться дважды.

## Источник истины

Приоритет при расхождении:

1. `openspec/specs/` — действующие спецификации.
2. `openspec/changes/` — принятые изменения и их delta-спеки.
3. `specs/001-token-estimator/spec.md` — версия 5.0, исходный канонический документ.
4. `README.md` — описание текущего поведения и измеренные результаты.

`specs/001-token-estimator/openjiuwen.md` и `*.tasks.yaml` — исторические материалы
v4.0; они не являются источником требований. Если README противоречит спеке —
прав код и спека, README приводится в соответствие.

## Рабочий цикл

1. `/opsx:explore` — прочитать спеку, код и тесты; ничего не менять.
2. `/opsx:propose` — оформить change с delta-спекой (`ADDED`/`MODIFIED`/`REMOVED`).
3. `/opsx:apply` — реализовать строго по `tasks.md` изменения.
4. `/opsx:archive` — после приёмки обновить спеку и убрать change в архив.

Код меняется только через change: нет change — нет правки. Новое требование сначала
попадает в delta-спеку, затем в код. Один change — одна цель.

## Жёсткие запреты

- Вводить лимит или `token_budget` на отдельную задачу: бюджет только общий.
- Использовать локальные нейросетевые модели и любые внешние LLM-endpoints.
- Ходить в сеть, кроме запросов к `LLM_BASE_URL`; в estimator, planner, unit-тестах
  и offline-режиме сетевых LLM-вызовов нет.
- Создавать служебные файлы в каталоге задачи: там допускается только `answer.txt`.
- Молча подменять модель или endpoint при ошибке шлюза; неразрешённый fallback запрещён.
- Править проверяющие тесты во время решения задачи; их хеши защищены.
- Коммитить секреты, `team.json`, API-ключи, токены и приватные URL.
- Перерегистрировать агента: регистрация неизменяема.
- Делать `git push` без явного разрешения владельца репозитория.

## Обязательные команды перед коммитом

```bash
python3.11 -m unittest discover -s tests
python3.11 -m unittest discover -s tests/contract
python3.11 run_agent.py --tasks-dir examples/task-dir --offline --max-workers 1
python3.11 run_agent.py --tasks-dir examples/task-dir-extended --offline --max-workers 1
npx --yes @fission-ai/openspec@1.17.0 validate add-token-estimator --strict
git grep -nE 'oc_sk_|BEGIN OPENSSH|API_KEY=|sk-[A-Za-z0-9]{20,}' -- ':!tests' ':!*.md'
```

Офлайн-прогон на `examples/task-dir` должен давать 8/8 и score 20; расширенный набор
— 16 задач без регрессии. Совпадения secret grep разбираются, а не игнорируются.
`openspec validate --strict` обязателен для каждого изменения.

## Определение готовности

Задача готова только при одновременном выполнении:

1. тест написан и падал до фикса, проходит после;
2. команда проверки из `tasks.md` прогнана, exit code и вывод приложены;
3. артефакт записан в ожидаемое место;
4. сделан коммит с сообщением `<task-id>: <краткое описание>` и известен его id;
5. измеренные числа внесены в отчёт, а не заявлены словами.

## Стоп-условия

- Сломаны базовые тесты или offline baseline — сначала зелёный baseline, потом работа.
- Три неудачные попытки подряд — откат к последнему зелёному состоянию, статус `blocked`.
- Наступило 12.11.2026 18:00 MSK — заморозка: только фиксы, ломающие приёмку.
- Секрет попал в дифф — стоп, отзыв ключа, очистка истории до пуша.
- Нарушен бюджетный инвариант или обнаружен перерасход — стоп и разбор ledger.

## Правило улучшений

Любое улучшение estimator, planner, solver или модели включается по умолчанию только
если выигрывает на отложенных данных при сопоставимом бюджете и не нарушает
бюджетный инвариант. Если выигрыш не подтверждён измерением — изменение
откатывается; сложная теория без воспроизводимого результата не принимается.
