# Прогноз стоимости задачи в токенах

## Purpose
Дать планировщику и бюджетной политике числовой прогноз расхода на задачу до её выполнения, чтобы решения о приёме и остановке опирались на измеримые ожидания. Прогноз — инструмент выбора, а не самостоятельная цель: баллы начисляются за решённые задачи.

## ADDED Requirements

### Requirement: Прогноз до вызова
Система SHALL выдавать по каждой задаче до первого обращения к модели прогноз ожидаемого входного и выходного расхода, ожидаемой стоимости и верхней границы стоимости.

#### Scenario: Задача с накопленной историей
- **WHEN** задача поставлена в план и для её семейства есть сопоставимые фактические наблюдения
- **THEN** система возвращает ожидаемый входной расход, ожидаемый выходной расход, ожидаемую стоимость и верхнюю границу стоимости

#### Scenario: Верхняя граница как эвристика
- **WHEN** прогноз выдаётся пользователю или планировщику
- **THEN** верхняя граница помечена как эвристическая оценка риска и не представлена как гарантия покрытия

### Requirement: Учёт промпта и шаблона ответа
Система MUST оценивать входной расход по тексту, который действительно уходит в модель, а выходной расход SHALL оценивать по ожидаемому формату ответа и числу шагов решателя.

#### Scenario: Prompt из нескольких частей
- **WHEN** промпт состоит из системной инструкции, инструкции задачи и содержимого файлов
- **THEN** прогноз входного расхода учитывает все эти части, а файлы вне контекста его не увеличивают

#### Scenario: Ответ в свободной форме
- **WHEN** задача ожидает короткий текстовый ответ
- **THEN** прогноз выходного расхода соответствует этому формату, а не единому фиксированному значению

#### Scenario: Многошаговое исправление кода
- **WHEN** задача предполагает несколько циклов правки и проверки
- **THEN** прогноз выходного расхода учитывает ожидаемое число шагов

### Requirement: Онлайн-коррекция по факту
После каждого ответа модели система SHALL пересчитывать оценки ещё не начатых задач по фактическому расходу, не изменяя уже зафиксированные факты.

#### Scenario: Факт отличается от прогноза
- **WHEN** фактический расход оказался выше прогноза
- **THEN** множитель коррекции для соответствующего семейства задач обновляется и последующие оценки пересчитываются

#### Scenario: Записанный факт неизменен
- **WHEN** коррекция применена после ответа
- **THEN** ранее записанные фактические значения расхода остаются без изменений

### Requirement: Офлайн-работа оценщика
Оценщик MUST работать офлайн, не выполнять LLM-вызовов и не обращаться к сети, а при одинаковых признаках и одинаковых калибровочных данных выдавать одинаковый прогноз.

#### Scenario: Прогноз в offline-режиме
- **WHEN** система запущена в offline-режиме
- **THEN** оценщик строит прогнозы без сетевых запросов и без обращений к модели

#### Scenario: Повторный расчёт
- **WHEN** один и тот же набор признаков оценивается дважды
- **THEN** результаты совпадают

### Requirement: Уровень уверенности и факторы
Система SHALL указывать для каждого прогноза уровень уверенности из набора low, medium и high, а также перечень факторов, определивших оценку.

#### Scenario: Достаточно наблюдений
- **WHEN** для семейства задач накоплено много сопоставимых фактических наблюдений
- **THEN** прогноз получает высокий уровень уверенности и непустой перечень факторов

#### Scenario: Мало наблюдений
- **WHEN** сопоставимых наблюдений мало
- **THEN** прогноз получает низкий уровень уверенности и более широкую верхнюю границу

### Requirement: Нулевой прогноз для детерминированных задач
Для задач, полностью покрываемых детерминированным решением, система MUST выдавать нулевой прогноз расхода и MUST NOT инициировать вызов модели.

#### Scenario: Задача решается без модели
- **WHEN** задача распознана как полностью детерминированная
- **THEN** прогноз стоимости равен нулю и обращений к модели не происходит

#### Scenario: Паттерн не подтвердился
- **WHEN** детерминированный решатель не может корректно обработать задачу
- **THEN** задача передаётся следующему решателю, а прогноз пересчитывается как ненулевой

### Requirement: Консервативный fallback при отсутствии данных
При отсутствии пригодных наблюдений система MUST выдавать консервативную оценку на основе доступных признаков с низкой уверенностью, а не выдуманное точное число.

#### Scenario: Нет истории по типу задачи
- **WHEN** для типа задачи нет валидных наблюдений
- **THEN** система применяет общий запасной прогноз, помечает его низкой уверенностью и расширяет верхнюю границу

#### Scenario: Данные непригодны
- **WHEN** имеющиеся записи не содержат фактического расхода
- **THEN** такие записи не используются как наблюдения и не подменяются нулевыми значениями

### Requirement: Область применимости метрик ошибки
Система SHALL вычислять MAPE только на задачах с положительным фактическим расходом и MUST показывать задачи с нулевым расходом отдельно.

#### Scenario: Смешанная выборка
- **WHEN** в выборке есть задачи с нулевым и с положительным фактическим расходом
- **THEN** MAPE считается только по положительным, а доля нулевых показывается отдельно

#### Scenario: Только нулевые расходы
- **WHEN** все наблюдения имеют нулевой фактический расход
- **THEN** MAPE не вычисляется и помечается как неприменимая
