# Design

## Context

Харнесс уже работает: 113 юнит-тестов (2 пропущены на хосте) и 29 контрактных
— все зелёные; офлайн-прогон с `--mutation-repair` даёт 8/8 и score 20 при нуле
токенов. `openjiuwen==0.1.20.post1` закреплён в `requirements.txt`, но на
рабочей машине SDK не установлен и живого ключа нет — проверки идут через
mock-прокси и записанные факты. В образе L1-слой проверен против прокси, L2
(DeepAgent) реализован и не подключён к раннеру.

Чего нет: `planner.estimate_cost()` — эвристика 40/60/80/1800 для сортировки, без
калибровки, интервала, уверенности и логирования; для неизвестного `task_type`
нет запасного солвера; политика «принять/отклонить» сводится к проверке
остатка; правки кода идут перезаписью файла целиком. Второй полигон — lorne
(`/home/eq/techlb/TCA`): 20 задач с проверками, 620 строк бенчмарка (5 моделей,
326 валидных `tokens_in`, 5,75 млн токенов, решаемость 48,9%) и 20 scripted-трейсов.

## Goals / Non-Goals

**Goals:**

- Поднять score при бюджетах 20k/50k/100k и удержать ноль перерасходов — это
  главный критерий изменения.
- Принимать/отклонять задачи по экономике, а не по интуиции; у каждого вердикта
  есть причина.
- Дать прогноз стоимости как инструмент планировщика: число, интервал,
  уверенность, факторы; обновлять его по ходу решения.
- Закрыть неизвестный тип задачи универсальным солвером и не терять задачу.
- Снизить стоимость coding-решений через SEARCH/REPLACE и петлю возврата ошибки.
- Уложиться в 50 мс на прогноз, работать офлайн и детерминированно.
- Предъявить измеримый эксперимент: score и coverage первичны, MAPE и PICP —
  диагностика; бейзлайны B0–B4, второй полигон lorne.
- Доказать использование openJiuwen SDK реальным smoke-тестом и решить судьбу
  DeepAgent по числу, а не по вере.

**Non-Goals:**

- Fine-tuning, обучение больших моделей, UI, мультиагентная оркестрация.
- Новые runtime-зависимости и замена солверов, которые уже решают 8/8 офлайн.
- LLM-вызов внутри прогноза как основной путь.
- Перерегистрация агента, любые `register_agent`/`deregister_agent`.
- Абсолютная точность прогноза: цель — дисциплина бюджета и score, а не MAPE
  ради MAPE.

## Decisions

### 1. Heuristic-first с калибровкой, сложные модели только по выигрышу

Стартуем с T1 (медиана по типу), T13 (символы→токены) и T19 (приоры lorne),
затем T2/T3/T4. Если T1 даёт MAPE ≤ 20%, сложные модели не добавляем (гейт Г2).
**Почему:** 8 официальных примеров и 50 синтетических — слишком мало для
нейросети; калибровка на train даёт защиту от переобучения. **Альтернативы:**
сразу log-linear (T3) — риск переобучения; сразу LLM-самооценка (T8) — платно и
ломает офлайн-требование.

### 2. Конформные интервалы вместо параметрических

Считаем остатки `r = y/ŷ` на калибровке, берём q10/q90, интервал `[ŷ·q10, ŷ·q90]`,
верхняя граница идёт в политику. **Почему:** распределение стоимости скошено
вправо, нормальное приближение занижает хвост, а именно хвост пробивает бюджет.
**Альтернативы:** bootstrap-CI (дороже и не даёт готовой границы для решения);
фиксированный запас +50% (грубее, режет score).

### 3. Cost-sensitive accept/reject с теневой ценой бюджета

Принимаем, если `reward·P_solve − λ·E[cost] > 0` и `upper + reserve ≤ remaining`;
иначе `reject:cost`. λ подбирается на калибровке. **Почему:** бюджет дефицитен,
порог по верхней границе игнорирует ожидаемую выгоду и пропускает выгодные
задачи. **Альтернативы:** «берём всё» (перерасходы), порог по `hi` (теряет
score), фиксированный порог reward/cost (не учитывает остаток).

### 4. SEARCH/REPLACE вместо full-file patch

Модель возвращает блоки поиска/замены; применяем лестницей: точное совпадение →
trim пробелов → нормализация отступов → кавычки/переводы строк → AST-якорь →
сходство ≥ 0,92. Требуем уникальность, при промахе возвращаем `closest_window`.
**Почему:** перезапись файла целиком дороже по completion и хрупче на слабых
моделях. **Альтернативы:** unified diff (нужна нумерация строк, чаще ломается);
оставить full-file (текущее поведение как fallback).

### 5. Verify-feedback: дословная ошибка в промпт

После правки: синтаксис → линтер (если есть) → связанные тесты; первая строка
`FAILED` идёт в следующий промпт без пересказа, максимум 6 итераций, хеши
тестовых файлов проверяются и восстанавливаются. **Почему:** модель чинит по
точному тексту ошибки быстрее, чем по пересказу; защита хешей исключает
«починку» теста. **Альтернативы:** пересказ ошибки (теряет детали); 3 итерации
(дешевле, но ниже решаемость — включается как деградация при росте стоимости).

### 6. Generic one-shot solver как fallback

Неизвестный тип → один вызов LLM, извлечение ответа/JSON с восстановлением,
таймаут и лимит токенов. **Почему:** сейчас такая задача просто падает, теряя
reward; один вызов — минимальная цена закрытия дыры. **Альтернативы:** эскалация
до сильной модели (дороже); детерминированный парсер (не покрывает произвол).

### 7. Реестр реализаций и `OJ_*`

`harness/registry.py` собирает оценщик, политику и солверы по имени;
`OJ_ESTIMATOR`, `OJ_POLICY`, `OJ_SOLVER` задают реализацию, дефолт —
калиброванные эвристики. **Почему:** ТР-17 требует замены без правки
вызывающего кода, а эксперименты с neural/DeepAgent не должны трогать раннер.
**Альтернативы:** `if/else` в `planner.py` (расползается по коду); monkey-patch
в тестах (непроверяемо).

### 8. Офлайн-прогноз: 50 мс, без сокетов

Оценщик не делает сетевых вызовов, не пишет на диск, использует stdlib;
нейросетевой вариант — локальные веса ≤ 5 МБ и откат на эвристику при любой
ошибке. **Почему:** П-2/ТР-09/ТР-18; иначе прогноз сам становится источником
стоимости и задержки. **Альтернативы:** LLM-прогноз (T8) только как
исследовательская ветка с отдельным бюджетом.

### 9. Второй полигон lorne как отложенная выборка

16–18 задач с манифестом и структурными проверками; 326 валидных строк
бенчмарка — приоры T19 и материал для проверки смещения. **Почему:** 8 примеров
не дают оценить обобщение, а lorne уже содержит проверки и факты. **Альтернативы:**
только синтетика (риск подгонки под генератор); только официальные примеры
(переобучение).

### 10. openJiuwen SDK как L1, DeepAgent только при выигрыше

Runtime идёт через `harness/ojiuwen_llm.py`; бэкенд фиксируется в stderr и в
`llm_backend`; DeepAgent (O3) пробуется на двух задачах с лимитом 6000 и
подключается только при выигрыше по score или стоимости. **Почему:** L1 уже
проверен, L2 не отлажен end-to-end, а бюджет и время ограничены. **Альтернативы:**
сразу DeepAgent в раннере (риск потери решаемости); только stdlib (не выполняет
требование конкурса).

### 11. Детерминированные типы за 0 токенов

`math`, `search`, `data_analysis` решаются без LLM; LLM — запасной путь, triage
отсекает невыполнимые. **Почему:** П-8 и измеренный офлайн 8/8 при 0 токенов;
каждый сэкономленный токен увеличивает число задач в бюджете. **Альтернативы:**
LLM для всех типов (дороже и медленнее); triage без порога (пропускает
невыполнимые).

### 12. Один сбор фактов, разбиение 70/30, калибровка только на train

Факты пишутся один раз в `eval/results/ground_truth.jsonl`, калибровка и выбор
модели — на train, отчёт — на holdout; волны В0–В3 с жёстким стопом 150k.
**Почему:** иначе метрики становятся оптимистичными и решение по гейтам
недействительно. **Альтернативы:** онлайн-обучение на всех данных (утечка);
несколько прогонов без фиксации seed (несравнимо).

### Решение: иерархия целей

Главный критерий — score и ноль перерасходов. MAPE, PICP и калибровка подчинены
политике планирования: если модель прогноза улучшает MAPE, но ухудшает score или
coverage, она отклоняется. Альтернатива — оптимизировать MAPE как
самостоятельную цель — отвергнута: это не соответствует регламенту соревнования.

### Решение: путь интеграции openJiuwen

Проверяем два пути одним smoke-тестом: низкоуровневый `Model` +
`ModelClientConfig`/`ModelRequestConfig` (используется сейчас) и официальный
`WorkflowAgent` + `Runner`. Выбираем тот, который даёт реальный вызов через
прокси, корректный `usage` и не ломает batch-раннер. Установка пакета без
реального вызова доказательством не считается.

## Theory Portfolio

|---|---|---|---|
| T1 | Приор по типу | Медиана по типу точнее константы | MAPE ≤ 20% → сложные модели не нужны |
| T2 | Учёт промпта | Промпт — основная часть стоимости | Ошибка промпта ≤ 10% на 7 из 8 |
| T3 | Степенная модель | Длина и файлы дают сигнал | Не лучше T1 → выкинуть |
| T4 | Цикл починки | Число попыток ~ Geometric(p) | Покрытие q80 < 60% → только медиана |
| T5 | Онлайн-обновление | Остаток прогнозируется лучше статики | Выигрыш < 5% → убрать |
| T6 | Конформные интервалы | Верхняя граница убирает перерасходы | PICP@90 < 75% → точечный + запас 50% |

| T14 | Поиск/замена | Патч фрагментом дешевле перезаписи | Нет выигрыша по score и cost → откат |

| T18 | Память эпизодов | Пример патча помогает похожей ошибке | Дороже +20% → выключить |

## Experiment Protocol

**Данные.** 8 официальных примеров — дымовой прогон; 40–60 синтетических задач
(по 10 на тип, seed 42) — обучение и валидация; 16–18 задач lorne — отложенный
набор. Факты собираются один раз в `eval/results/ground_truth.jsonl`, разбиение
70/30, калибровка только на train.

**Метрики.** MAPE, MdAPE, смещение (прогноз/факт), Pinball, PICP@90, MPIW,
число перерасходов (цель 0), score при 20k/50k/100k, сожаление решения,
задержка прогноза.

**Бейзлайны.** B0 — константа 1000; B1 — медиана по типу; B2 — текущая
эвристика 40/60/80/1800; B3 — калиброванная T2+T3; B4 — победитель на отложенной
выборке.

**Волны (жёсткий стоп 150k).** В0 — факты по 8 примерам, токенайзер, T1, T13
(~10k); В1 — синтетика и факты, T2, T3, T4, T9, офлайн-проверка T14/T15 (~70k);
В2 — T5, T6, T7, T10, абляции, симуляции 20/50/100k, T19 (~40k); В3 — T8, T17,
T11 только при разрешении организаторов (≤ 30k).

**Гейты.** Г1 (после В0): есть ли офлайн-токенайзер — определяет основу T2.
Г2 (после В1): T1 с MAPE ≤ 20% → заморозка простой модели. Г3 (после В2): выбор
модели по holdout при PICP@90 ≥ 0,85 и нуле перерасходов, score при 20k не хуже
бейзлайна. Г4: теория, не прошедшая критерий отказа, публикуется как
отрицательный результат.

**Статистика.** Bootstrap 2000 пересэмплирований для доверительных интервалов
метрик, парный критерий Уилкоксона по ошибкам задач; при малом n — медианы и
межквартильный размах. Гипотезы и критерии отказа фиксируются до прогонов.

## Risks / Trade-offs

- **Официальная команда запуска неизвестна** → параметризуем entrypoint и
  используем дефолт `python /app/run_agent.py --tasks-dir /data/tasks`.
- **«openJiuwen» могут понимать как Swarm, а не SDK** → два entrypoint:
  L1 в раннере, `jiuwenswarm-batch.sh` как обёртка с harness-отчётом.
- **На машине нет живого ключа и SDK** → живые проверки через mock-прокси и
  записанные факты; результаты помечаются как гипотеза до подтверждения.
- **Три дня и заморозка 12 ноября 18:00** → скоуп ограничен лейнами раздела 6,
  всё вне — в README как «не сделано».
- **Переобучение на 8 примерах** → синтетика 40–60 задач плюс отложенный lorne,
  калибровка только на train, гейт Г2.
- **Потеря регистрации** → никаких `register_agent`/`deregister_agent`, только
  heartbeat; проверка чек-листом перед сдачей.
- **Утечка секретов** → `git grep` на `oc_sk_|API_KEY=|BEGIN OPENSSH`,
  `.gitignore`, `team.json` не коммитится; ключ не логируется.
- **Бюджет экспериментов может уйти на живые вызовы** → стоп на 150k, дальше
  только записанные факты; T8/T11/T17 — последняя волна.
