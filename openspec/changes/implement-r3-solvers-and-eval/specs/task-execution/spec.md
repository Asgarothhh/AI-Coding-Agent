# Spec Delta: task-execution (R3)

## Purpose
Загрузка официальной схемы задач без потери полей, безопасное разрешение путей, маршрутизация solver и обязательный файл ответа в каталоге задачи.

## ADDED Requirements

### Requirement: Полный raw task.json сохраняется
Система MUST сохранять исходный decoded объект `task.json` целиком (включая неизвестные поля и `expected`) и MUST NOT терять их при нормализации. Production MUST NOT использовать `expected` как ответ.

#### Scenario: Незнакомое поле
- **WHEN** `task.json` содержит дополнительный ключ, неизвестный текущей версии
- **THEN** задача загружается, ключ доступен в сохранённом raw-объекте и не вызывает ошибку разбора

#### Scenario: Некорректный JSON или отсутствующее обязательное поле
- **WHEN** файл не является JSON-объектом или отсутствует одно из полей `task_id`, `task_type`, `instruction`, `reward`, `check`
- **THEN** каталог пропускается с диагностикой, прогон остальных задач продолжается, случайный ответ не записывается

### Requirement: Reward читается явно
Система MUST читать `reward` как число и MUST NOT использовать его как признак сложности или решаемости.

#### Scenario: Числовой reward
- **WHEN** `reward` задан числом
- **THEN** значение доступно планировщику как награда за решение

#### Scenario: Нечисловой reward
- **WHEN** `reward` имеет нечисловой тип
- **THEN** задача не загружается как валидная и получает диагностический статус

### Requirement: Безопасное разрешение путей задачи
Система MUST разрешать файлы задачи только внутри каталога задачи и MUST NOT следовать path traversal, symlink escape или неожиданному абсолютному пути за пределы каталога.

#### Scenario: Попытка выхода из каталога
- **WHEN** путь содержит `..`, абсолютный префикс вне каталога задачи или symlink, ведущий наружу
- **THEN** путь отклоняется и не используется для чтения или патча

### Requirement: Разделение разбора и выбора solver
Система MUST отделять разбор/валидацию `task.json` от выбора solver. Невалидная структура MUST NOT приводить к уверенному ответу.

#### Scenario: Неизвестный task_type
- **WHEN** `task_type` не входит в известный набор `math`, `search`, `data_analysis`, `coding`
- **THEN** задача остаётся загруженной и передаётся универсальному решателю

### Requirement: Deterministic unmatched уходит в generic
Если детерминированный solver не нашёл подтверждаемый шаблон, система MUST NOT выдавать уверенно неверный ответ. При доступном LLM-шлюзе система MUST передать задачу универсальному решателю.

#### Scenario: Шаблон не подошёл и LLM доступен
- **WHEN** `task_type` равен `math`, `search` или `data_analysis`, детерминированный solver вернул отсутствие ответа, и LLM доступен
- **THEN** задача обрабатывается универсальным решателем, а не помечается как уверенно решённая неверным значением

#### Scenario: Шаблон не подошёл в offline
- **WHEN** детерминированный solver не нашёл шаблон и LLM недоступен
- **THEN** задача не считается solved, расход токенов равен нулю

### Requirement: Пустой answer.txt на старте
Для каждой загруженной задачи система MUST обеспечить наличие `<TASKS>/<task_id>/answer.txt`. Если файла нет, система MUST создать пустой файл. Пустой файл MUST NOT учитываться как solved.

#### Scenario: Каталог без ответа
- **WHEN** в каталоге задачи нет `answer.txt` в начале обработки
- **THEN** система создаёт пустой файл по официальному пути

#### Scenario: Подтверждённое решение
- **WHEN** solver вернул непустой подтверждённый ответ
- **THEN** файл атомарно заменяется содержимым ответа и задача учитывается как solved
