# Spec Delta: coding-repair (R3)

## Purpose
Безопасный цикл правки кода: минимальный однозначный патч, лимит попыток, защита проверяющих файлов и честный провал без фиктивного solved.

## ADDED Requirements

### Requirement: SEARCH/REPLACE только при одном совпадении
Система MUST применять SEARCH/REPLACE только при ровно одном совпадении SEARCH. При 0 совпадениях система MUST вернуть короткий `closest_window` и MUST NOT менять файл. При более чем одном совпадении система MUST отказать и MUST NOT менять файл.

#### Scenario: Точное единственное совпадение
- **WHEN** SEARCH встречается в целевом исходнике ровно один раз
- **THEN** REPLACE применяется и исходный перевод строк/кодировка сохраняются

#### Scenario: Совпадений нет
- **WHEN** SEARCH не найден даже после безопасной нормализации пробелов и переводов строк
- **THEN** файл не изменяется, а следующему шагу возвращается ближайший фрагмент

#### Scenario: Несколько совпадений
- **WHEN** SEARCH совпадает более чем в одном месте
- **THEN** правка не применяется

### Requirement: Запрет опасных путей патча
Система MUST отклонять path traversal, symlink escape и изменение проверяющих файлов. Несколько операций MUST быть транзакционными: при ошибке исходные файлы MUST остаться неизменными.

#### Scenario: Попытка изменить тест
- **WHEN** патч указывает на `test_*.py` или `*_test.py`
- **THEN** правка отклоняется, попытка не может быть засчитана успешной

#### Scenario: Частичный отказ нескольких hunks
- **WHEN** одна из нескольких операций SEARCH/REPLACE не применяется
- **THEN** ни одна операция этой транзакции не остаётся в файлах

### Requirement: Не более трёх итераций ремонта
Система MUST ограничивать цикл LLM-ремонта тремя итерациями по умолчанию и MUST прекращать цикл при достижении предела. После каждой неудачи система MUST передать в следующий запрос первую диагностическую ошибку и компактный контекст.

#### Scenario: Три неудачи
- **WHEN** три попытки LLM-патча не прошли проверку
- **THEN** четвёртая попытка не выполняется, тесты восстановлены к baseline, задача не solved

#### Scenario: Успех на второй попытке
- **WHEN** проверка проходит на второй итерации
- **THEN** третья итерация не запускается и ответ сохраняется как DONE только после прохождения тестов

### Requirement: Честный провал без фиктивного solved
При исчерпании попыток или подмене oracle система MUST NOT учитывать задачу как solved. Пустой `answer.txt` MAY существовать по контракту пути и MUST NOT считаться решением.

#### Scenario: Все попытки неудачны
- **WHEN** ни одна попытка не прошла проверку
- **THEN** статус failed, `solved_count` не увеличивается, файл ответа пуст или отсутствует содержательный ответ

#### Scenario: Проверки подменены
- **WHEN** хеши проверяющих файлов отличаются от baseline после попытки solver
- **THEN** изменённые solver-ом тесты восстанавливаются, результат не принимается
